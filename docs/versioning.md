# Nero 버전 관리

## 기준

- 새 데스크톱 앱의 배포 기준은 `0.0.1`이다. 이후 버전은 증가시키며 같은 버전의 배포 파일을 다른 내용으로 덮어쓰지 않는다.
- `0.x`에서도 기존 Nero 데이터를 읽고 보존하는 것을 릴리스 계약으로 둔다. 초기 버전이라는 이유로 저장 형식을 임의로 깨지 않는다.
- 이전 로컬 테스트 앱의 `0.1.0` 표시는 이번 기준 정리의 예외다. `0.0.1`로 바꾸어도 앱 식별자, 데이터 경로와 저장 스키마를 초기화하거나 새 라이브러리를 만들지 않는다. 향후 업데이트/설치기의 버전 비교에서 이 숫자 변경을 자동 업그레이드로 간주하지 않는다.
- 보관된 Legacy Swift 앱의 버전과 데이터는 별도 제품 이력이다. 새 앱에서 암묵적으로 탐색하거나 이관하지 않는다.

## 번호

| 구분 | 규칙 |
|---|---|
| 제품 버전 `MAJOR.MINOR.PATCH` | `PATCH`는 호환 버그 수정, `MINOR`는 호환 기능 추가, `MAJOR`는 명시적인 비호환 계약 변경. `0.x`에도 동일한 데이터 보존 규칙 적용 |
| 배포 빌드 | `1`부터 시작하는 양의 정수. 제품 버전과 독립적으로 전체 릴리스에서 증가시키며 재사용하지 않음. 같은 제품 버전의 검증용 재빌드도 구분하되, 이미 배포한 파일은 보존하고 다음 배포에는 새 제품 버전을 사용 |
| 저장 스키마 | 제품 버전과 독립. 저장 필드/값/의미가 바뀌는지로 결정하며 제품 번호만 바뀌면 올리지 않음 |
| 문서 수정 회차 | `TranscriptVersion.revision`은 해당 음성 기록의 편집 회차. 제품/스키마 버전으로 사용하지 않음 |
| 모델/프롬프트 | 모델 revision/SHA256, 실행기, `promptVersion`, 템플릿을 결과에 보존. 앱 버전으로 대체하지 않음 |

제품 버전의 정본은 `apps/desktop/package.json`의 `version`이다. `node apps/desktop/scripts/version.mjs set <version> --build <number>`로 Tauri 설정, 두 Rust 패키지와 npm/Cargo 잠금 파일을 함께 갱신하고, `node apps/desktop/scripts/version.mjs check`로 일치 여부를 검사한다.

- macOS는 제품 버전을 표시 버전으로, `bundle.macOS.bundleVersion`을 `CFBundleVersion`으로 사용한다. 이번 제품 기준은 `0.0.1`이며 최종 배포 빌드는 릴리스 이력에서 확인한다.
- Windows NSIS 설치 버전은 제품 버전 `0.0.1`이다. 독립 빌드 번호는 배포 파일명/영수증에 기록한다. 별도 네 번째 설치 버전 필드가 구현됐다고 가정하지 않는다.
- 내부 패키지명과 이벤트명이 `grove`인 것은 이름 변경과 별개다.
- 릴리스 태그는 `nero-v<제품 버전>`으로 최종 릴리스 구성 커밋에 붙인다. 배포 검증 후 생성하고 이미 사용한 태그를 이동하거나 재사용하지 않는다. 이미 공증된 앱을 컨테이너만 다시 포장하면 앱 소스와 포장 도구 커밋을 각각 기록한다. 문서만 후속 커밋으로 보강해도 배포본의 소스 해시는 바꾸지 않는다.

## 데이터 계약

현재 코드 기준:

| 대상 | 현재 계약 |
|---|---|
| 앱 식별자 | `io.github.choseongmin1128.grove.desktop` 유지 |
| 저장 루트 | Tauri `app_data_dir()`. macOS는 `~/Library/Application Support/<identifier>`, Windows는 해당 사용자의 앱 데이터 디렉터리. 제품 이름/버전으로 새 경로를 조립하지 않음 |
| 회의 `meeting.json` / 녹음 `manifest.json` | `store.rs`의 `SCHEMA_VERSION = 1`; 다른 schemaVersion은 현재 읽기 거부 |
| 음성 기록/회의록 | 별도 schemaVersion 필드 없음. `Transcript`, `TranscriptSegment`, `Summary`의 JSON 구조가 현재 계약이며, 수정 회차/원문 해시는 별도로 저장 |
| 추가된 선택 필드 | `meetingDate`, `recordedAt`, `warning`, 녹음 `quality`는 없는 기존 데이터를 기본값으로 읽음 |
| 원본 | 녹음 PCM, 가져온 원본, 모델 원출력을 보존. 수정본/회의록은 별도 결과로 저장 |

데이터를 쓰는 경로는 `CoreHandle`의 직렬 처리와 `Store` 잠금을 통한다. CLI 등 새 진입점을 추가해도 별도 저장소 writer를 만들지 않는다. JSON 교체는 완전한 임시 파일을 쓴 뒤 수행하는 기존 경로를 사용한다.

## 변경 규칙

1. 저장 필드의 추가/삭제/이름/타입/의미, enum 값, 경로와 ID, 원문 해시에 영향을 주는 직렬화 변경을 먼저 확인한다. 메모리 안에서만 쓰는 DTO 변경과 구분한다.
2. 누락 가능한 필드 추가는 기존 파일에서 기본값으로 읽을 수 있게 한다. 필수 필드나 enum 값 변경은 단순 선택 필드 추가로 취급하지 않는다.
3. 새 코드가 이전 릴리스 데이터를 읽고 편집/재개방해도 원음, 메모, 수정본, 회의록의 출처 연결을 보존해야 한다. 실제 사용자 원문을 공개 테스트에 넣지 않는다.
4. 형식 변환이 필요하면 입력 형식과 출력 형식을 명시하고, 원본 백업, 쓰기 실패/중단, 재실행을 검증한다. 원본을 제자리에서 파괴하지 않는다. 아직 필요하지 않은 마이그레이션 프레임워크를 미리 만들지 않는다.
5. 지원하지 않는 형식/버전은 오류로 알리고 데이터를 보존한다. 읽기 실패를 빈 라이브러리로 처리하거나 자동 삭제/초기화하지 않는다.
6. 모델을 바꾸거나 재처리해도 기존 결과를 삭제하지 않는다. 전사 수정 버전/해시와 다르면 회의록이 오래된 결과임을 유지한다.

현재 저장 구조는 `deny_unknown_fields`를 사용하므로, 새 앱이 추가한 필드를 오래된 앱이 읽는 역방향 호환은 보장되지 않는다. 이 정책의 기본 보장은 **새 버전이 이전 버전의 데이터를 보존하는 것**이다. 구버전으로 되돌릴 때는 그 구버전에 맞는 백업 사본을 별도 경로에서 사용해야 하며, 최신 데이터를 구버전으로 열어도 된다고 안내하지 않는다.

## 릴리스 확인

- 제품/플랫폼 버전, 앱 식별자, 저장 스키마, 모델/프롬프트 변경 여부를 확인한다.
- 저장 형식을 바꾸면 이전 배포 형식의 익명 fixture로 읽기, 수정, 재개방, 출처 연결을 검증한다. 현재 구조의 왕복 테스트만으로 이전 버전 호환을 통과 처리하지 않는다.
- 저장 형식이 그대로면 불필요한 마이그레이션을 실행하지 않는다. 실제 설치본 교체 시 원본 데이터/모델 보존 여부를 별도 확인한다.
- macOS 서명/공증/DMG와 Windows 설치/업데이트는 별도 검증이다. 한 운영체제의 통과를 다른 운영체제 통과로 기록하지 않는다.
- 소스 commit 전체 해시, dirty 여부, 빌드 번호, 산출물 SHA256, 대상 OS/아키텍처와 확인 범위를 이력에 기록한다. 미커밋 빌드는 기준 HEAD와 변경 소스 해시/패치를 보존하고, HEAD만으로 재현 가능하다고 쓰지 않는다.
- 배포 앱의 `Contents/Resources/build-info.json`과 ZIP/DMG 각각의 `.zip.receipt.json`/`.dmg.receipt.json`에 동일한 소스 정보를 남긴다. 실제 배포 서명은 미커밋 소스나 빌드 후 소스 변경을 거부한다.
- 소스 변경 이력과 실제 배포/공증/설치 상태를 구분한다. 존재하지 않는 커밋 해시나 아직 받지 않은 공증 승인을 기입하지 않는다.

변경 및 배포 기록은 [릴리스 이력](release-history.md)에 남긴다.
